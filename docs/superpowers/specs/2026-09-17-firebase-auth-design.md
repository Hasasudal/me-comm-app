# Firebase 학교 계정 인증 설계

## 목표

미컴 라운지는 누구나 첫 화면과 회원가입·로그인 화면에 접근할 수 있다. 게시판 목록, 게시글 본문, 글쓰기와 관리 기능은 Firebase에서 `@ks.ac.kr` 이메일 인증을 완료한 회원만 사용할 수 있다.

## 확정 요구사항

- 회원가입 필드는 이름, `@ks.ac.kr` 이메일, 비밀번호다.
- 이메일 주소의 실제 소유 여부는 Firebase Authentication의 인증 메일로 확인한다.
- 이메일 인증 전에는 게시판을 읽거나 작성할 수 없다.
- 기존 게시글 비밀번호 보호와 뉴스 승인 흐름은 유지한다.
- 관리자 초대 코드는 이메일 인증까지 완료한 회원만 사용할 수 있다.
- 회원은 이름과 학교 이메일을 변경하고 자신의 계정을 탈퇴할 수 있다.
- 관리자는 회원을 검색하고 미컴 라운지 이용을 정지하거나 복구할 수 있다.
- 인증·비밀번호 재설정·이메일 변경 화면과 안내 문구를 한국어로 제공한다.
- 사이트 접근 정책은 인증 기능을 배포하고 검증한 뒤 `public`으로 변경한다.

## 선택한 접근 방식

Firebase Authentication이 이메일·비밀번호 계정, 인증 메일, 비밀번호 재설정을 담당한다. 미컴 라운지 서버는 Firebase ID 토큰을 검증한 뒤 자체 D1 세션을 발급한다. 게시판 API는 Firebase SDK에 직접 의존하지 않고 D1 세션만 확인하므로, 인증 공급자와 게시판 권한 경계를 분리한다.

Resend는 사용하지 않는다. Firebase의 기본 인증 메일 발송을 사용하므로 별도 발신 도메인과 메일 API 키가 필요하지 않다.

## 사용자 흐름

### 회원가입과 이메일 인증

1. 사용자가 `/signup`에서 이름, 학교 이메일, 비밀번호를 입력한다.
2. 브라우저와 서버가 이메일을 소문자로 정규화하고 주소가 정확히 `@ks.ac.kr`로 끝나는지 확인한다. `@sub.ks.ac.kr`은 허용하지 않는다.
3. Firebase가 이메일·비밀번호 계정을 만들고 이름을 `displayName`으로 저장한다.
4. Firebase가 인증 링크를 학교 이메일로 발송한다.
5. 인증 링크 처리 후 사용자는 `/login?verified=1`로 돌아온다.
6. 사용자가 로그인하면 브라우저가 최신 Firebase ID 토큰을 서버의 세션 교환 API에 전달한다.
7. 서버가 토큰 서명, 발급자, 대상 프로젝트, 만료 시각, `email_verified`, 학교 이메일 도메인과 이름을 검증한다.
8. 서버가 D1 회원을 생성하거나 갱신하고 자체 세션 쿠키를 발급한다.

### 로그인과 로그아웃

- 로그인은 Firebase의 이메일·비밀번호 인증을 사용한다.
- 이메일 미인증 계정은 세션 교환이 거부되며 인증 메일 재발송 화면을 제공한다.
- 로그아웃은 D1 세션을 폐기하고 쿠키를 만료한 뒤 Firebase 클라이언트 세션도 종료한다.
- 비밀번호 재설정 메일은 Firebase가 발송한다.

### 프로필과 계정 관리

- 회원은 `/account`에서 이름을 변경할 수 있다. Firebase `displayName`을 먼저 갱신하고 새 ID 토큰으로 D1 이름을 동기화한다.
- 이메일 변경은 최근 로그인을 확인한 뒤 새로운 `@ks.ac.kr` 주소로 Firebase 인증 메일을 보낸다.
- 이메일 변경이 완료되면 기존 미컴 라운지 세션을 모두 폐기하고 새 주소로 다시 로그인하게 한다.
- 회원 탈퇴는 최근 로그인 확인 후 Firebase 계정을 삭제하고 D1의 세션, 관리자 권한과 회원 프로필을 정리한다.
- 게시글은 익명 게시글 비밀번호를 기준으로 관리하므로 회원 탈퇴 후에도 유지한다.

### 관리자 회원 관리

- 활성 관리자는 `/admin/members`에서 이름 또는 학교 이메일로 회원을 검색할 수 있다.
- 회원 정지는 `users.status`를 `suspended`로 바꾸고 해당 회원의 모든 D1 세션을 삭제한다.
- 정지 회원이 Firebase 로그인을 완료하더라도 서버의 세션 교환 API가 새 미컴 라운지 세션 발급을 거부한다.
- 관리자는 정지 회원을 다시 `active`로 복구할 수 있다.
- 관리자는 자신의 계정을 정지할 수 없으며 마지막 활성 관리자에게 영향을 주는 동작도 차단한다.
- Firebase 계정 자체의 강제 삭제는 Firebase Console에서만 수행하고 이번 웹 관리자 기능에는 포함하지 않는다.

### 게시판 접근

- 비회원은 서비스 소개, 회원가입, 로그인 화면만 이용할 수 있다.
- `/`, `/news`, `/clubs`, `/contests`는 비회원에게 가입·로그인 안내를 표시하며 게시글 목록을 요청하지 않는다.
- 게시글 목록, 상세 열람, 작성, 수정과 삭제 API는 유효한 회원 세션을 요구한다.
- 로그인 회원도 기존 정책대로 게시글 본문 열람·수정·삭제 시 게시글 비밀번호를 입력한다.
- 승인 대기 뉴스와 관리자 API는 회원 세션에 더해 활성 관리자 권한을 요구한다.

## 서버 인증 구조

### Firebase 설정

운영 환경에는 다음 공개 설정값을 둔다.

- `FIREBASE_API_KEY`
- `FIREBASE_AUTH_DOMAIN`
- `FIREBASE_PROJECT_ID`
- `FIREBASE_APP_ID`

클라이언트는 `/api/auth/config`에서 필요한 공개 설정만 받는다. Firebase 웹 API 키는 비밀키로 취급하지 않지만, Google Cloud Console에서 현재 사이트 도메인과 필요한 API로 사용 범위를 제한한다.

### ID 토큰 검증

서버는 Google의 Firebase 공개 키로 RS256 서명을 검증한다. 다음 조건을 모두 만족해야 한다.

- `alg`가 `RS256`이다.
- `kid`가 현재 공개 키에 존재한다.
- `aud`가 설정된 Firebase 프로젝트 ID와 같다.
- `iss`가 `https://securetoken.google.com/<project-id>`와 같다.
- `sub`가 비어 있지 않다.
- `exp`와 `iat`가 허용 범위에 있다.
- `email_verified`가 `true`다.
- 이메일이 정확히 `@ks.ac.kr` 도메인이다.
- 이름이 비어 있지 않다.

공개 키 응답은 제공된 캐시 만료 시간까지만 메모리에 보관하며, 알 수 없는 `kid`가 들어오면 한 번 새로 가져온다.

### 애플리케이션 세션

- 세션 토큰은 32바이트 이상의 암호학적 난수로 생성한다.
- D1에는 토큰 원문 대신 SHA-256 해시만 저장한다.
- 쿠키 이름은 `micom_session`이며 `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`를 적용한다.
- 세션 유효기간은 14일이며 로그인할 때 새 세션으로 교체한다.
- 로그아웃 시 해당 세션을 D1에서 삭제한다.
- 만료된 세션은 인증 요청 중 정리한다.
- 세션 조회 시 연결된 회원의 `status`도 확인하며 정지 회원의 세션은 즉시 무효화한다.

## 데이터 모델

### `users`

- `id`: Firebase UID, 기본 키
- `email`: 정규화된 학교 이메일, 고유 값
- `display_name`: 회원 이름
- `status`: `active` 또는 `suspended`
- `suspended_at`: 이용 정지 시각, 활성 상태에서는 `null`
- `created_at`: 최초 가입 시각
- `updated_at`: 최근 프로필 동기화 시각

### `sessions`

- `token_hash`: 세션 토큰 SHA-256 해시, 기본 키
- `user_id`: `users.id`
- `created_at`: 발급 시각
- `expires_at`: 만료 시각

기존 `admin_users.user_id`에는 Firebase UID를 저장한다. 운영 데이터베이스에 등록된 관리자가 아직 없으므로 별도 계정 마이그레이션은 필요하지 않다.

Firebase가 비밀번호와 이메일 인증 상태를 관리하므로 D1에는 회원 비밀번호 또는 비밀번호 해시를 저장하지 않는다.

## API 변경

- `GET /api/auth/config`: 공개 Firebase 웹 설정 반환
- `POST /api/auth/session`: 검증된 Firebase ID 토큰을 D1 세션으로 교환
- `DELETE /api/auth/session`: 현재 D1 세션 폐기
- `GET /api/session`: 로그인 여부, 회원 정보와 관리자 여부 반환
- `PATCH /api/account`: 새 Firebase ID 토큰으로 이름 또는 인증 완료된 학교 이메일 동기화
- `DELETE /api/account`: 현재 회원의 D1 세션, 관리자 권한과 회원 프로필 정리
- `GET /api/admin/users`: 이름·이메일 검색과 페이지 단위 회원 목록
- `PATCH /api/admin/users/:userId`: 회원 이용 정지 또는 복구
- 기존 게시판 API: `requireMember` 적용
- 기존 관리자 API: `requireAdmin`이 회원 세션과 `admin_users`를 함께 확인
- 기존 관리자 코드 등록: ChatGPT 헤더 대신 회원 세션의 Firebase UID를 사용

## 화면 변경

- `/signup`: 이름, 학교 이메일, 비밀번호, 비밀번호 확인과 인증 메일 안내
- `/verify-email`: 인증 메일 발송 완료, 재발송, 로그인 이동
- `/login`: 이메일·비밀번호 로그인, 이메일 미인증 안내, 비밀번호 재설정
- `/auth/action`: 이메일 인증, 비밀번호 재설정, 이메일 변경 취소를 처리하는 한국어 작업 화면
- `/account`: 이름·학교 이메일 변경, 비밀번호 재설정과 회원 탈퇴
- `/admin/members`: 회원 검색, 이용 정지·복구와 활성 관리자 관리
- 공통 헤더: 로그인 상태에서는 이름과 로그아웃, 비회원 상태에서는 로그인과 회원가입 표시
- 게시판 비회원 화면: 게시글 데이터 대신 학교 계정 가입 안내 표시
- 관리자 등록 화면: 학교 계정 로그인 상태를 기준으로 관리자 코드를 받음

기존 미컴 라운지 시각 체계와 모바일 레이아웃을 그대로 확장한다.

## 보안과 오류 처리

- 회원가입 화면과 서버 세션 교환에서 학교 이메일 도메인을 이중 검증한다.
- Firebase 오류 코드를 한국어 사용자 메시지로 매핑하고 내부 오류 세부 내용은 노출하지 않는다.
- 세션 교환, 로그인 UI, 인증 메일 재발송과 관리자 코드 입력에 요청 횟수 제한을 적용한다.
- 세션을 사용하는 변경 API는 기존 동일 출처 검사와 JSON 콘텐츠 유형 검사를 유지한다.
- 인증 실패는 `401`, 회원이지만 관리자 권한이 없으면 `403`을 반환한다.
- 이메일 존재 여부를 추측하기 어렵도록 비밀번호 재설정 결과는 동일한 안내 문구를 사용한다.
- 이름은 앞뒤 공백을 제거한 2~40자로 제한하고 화면 출력 시 텍스트로만 렌더링한다.
- 회원 정지·복구와 탈퇴는 감사 가능한 서버 로그를 남기되 이메일 전체나 토큰을 로그에 기록하지 않는다.
- 회원 탈퇴는 확인 문구와 최근 Firebase 재인증을 모두 요구한다.

## 테스트 전략

- Firebase 토큰 검증기는 테스트용 RS256 키로 정상 서명, 잘못된 서명, 발급자, 대상 프로젝트, 만료, 미인증 이메일과 잘못된 도메인을 검증한다.
- 회원 세션 통합 테스트는 로컬 D1에 테스트 회원과 해시 세션을 준비해 비회원 API 차단, 회원 목록·열람·작성, 로그아웃과 관리자 코드 등록을 확인한다.
- 페이지 테스트는 회원가입, 인증 안내, 로그인, 비회원 게시판 게이트를 확인한다.
- 계정 관리 테스트는 이름 동기화, 인증되지 않은 이메일 변경 차단, 탈퇴 후 세션 폐기를 확인한다.
- 관리자 회원 테스트는 이름·이메일 검색, 정지 즉시 세션 폐기, 정지 계정 재로그인 차단, 복구와 자기 정지 차단을 확인한다.
- 이메일 작업 화면은 인증, 비밀번호 재설정, 이메일 변경 복구 모드와 잘못된·만료된 코드를 확인한다.
- 기존 게시글 비밀번호, 뉴스 승인, 관리자 권한 테스트를 회원 세션 방식에 맞게 갱신한다.
- 실제 운영 배포 전 Firebase 테스트 학교 계정으로 가입, 인증 메일 수신, 인증 링크, 로그인과 게시판 접근을 수동 확인한다.

## 배포 순서

1. Firebase 프로젝트를 만들고 Email/Password 로그인을 활성화한다.
2. 현재 Sites 도메인을 Firebase 승인 도메인과 인증 메일 복귀 URL에 등록한다.
3. Firebase 공개 설정을 Sites 운영 환경 변수에 저장한다.
4. 데이터베이스 마이그레이션과 인증 기능이 포함된 버전을 소유자 전용 상태로 먼저 배포한다.
5. 운영 환경에서 학교 이메일 인증과 게시판 접근 제어를 확인한다.
6. 검증이 끝난 뒤 Sites 접근 정책을 `public`으로 변경한다.

Firebase 설정값이 준비되지 않으면 회원가입을 비활성화하고 설정이 필요하다는 운영 안내만 표시한다. 인증 경계가 없는 상태로 사이트를 공개하지 않는다.

## 범위 밖

- 학번 검증과 재학생 여부 조회
- 학교 포털 SSO
- 소셜 로그인
- 관리자의 Firebase 계정 강제 삭제
- 자체 이메일 템플릿 발송 서버
